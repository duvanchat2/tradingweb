# Decisiones y aclaraciones — Fase 1

- **Dominio:** `tradingweb.local`; Caddy sirve HTTP local en el puerto 8080. HTTPS público, DNS, backups y despliegue VPS corresponden a Fase 4. No se solicita ni utiliza un dominio externo.
- **Modo demo obligatorio:** se rechaza `DEMO_MODE=false`, incluso con `LIVE_LICENSE_KEY`. Es una restricción más fuerte que §5, acorde con la instrucción de mantener demo en todo momento; no existe implementación live.
- **Financiación de cuentas:** se añade `accounts.normal_side` y el tipo interno `system`. Las cuentas de patrimonio demo tienen naturaleza acreedora; los activos del cliente tienen naturaleza deudora. Todas empiezan en cero. `post_entry()` aumenta patrimonio virtual al emitir saldo demo mediante dos asientos cuya suma es cero. Ninguna cuenta puede tener saldo negativo. Estas cuentas internas no son cuentas operativas del superworker y no tienen routers públicos.
- **Ledger:** `amount` es firmado en `transactions`; valores negativos representan salida del activo o crédito al patrimonio. `entry_id` agrupa los dos asientos y `original_transaction_id` permite futuras correcciones compensatorias. Las transferencias requieren la misma moneda; un swap futuro deberá compensar cada moneda mediante cuentas internas. El servicio no confirma transacciones: el llamador controla commit/rollback, y un savepoint revierte la operación completa ante errores.
- **Seed:** se crean nueve cuentas principales por cada uno de los diez usuarios y nueve cuentas internas de patrimonio. Los 20 movimientos solicitados son 20 transferencias adicionales (40 asientos), además de asignaciones iniciales y un depósito simulado aprobado. Hay tres solicitudes de depósito, una pendiente, una aprobada y una rechazada. No se implementan retiros en esta fase. Las cuatro piezas KYC son archivos de texto explícitamente sintéticos.
- **Credenciales:** no se incluye una contraseña fija en código ni README. `infra/init_env.py` genera `SEED_PASSWORD`, compartida únicamente por los diez usuarios demo, y secretos locales en `.env` ignorado por Git. README documenta dónde consultarla. Los correos son `@demo.example.com` porque el validador EmailStr rechaza dominios reservados `.test`.
- **Sesiones:** JWT en Authorization, sin cookies; refresh rotativo y sesiones revocables en Redis con TTL. Una operación Lua hace la rotación atómica; reutilizar un refresh revoca su sesión. Logout revoca access y refresh de esa sesión. Roles públicos siempre son `client`; staff/superworker se aprovisionan con seed. Cookies HttpOnly/CSRF e interfaces de login se abordarán al integrar las interfaces, antes de cualquier uso productivo.
- **Frontends:** dos bases Next.js 14/App Router/TypeScript compilables, con banner persistente y páginas de estado en `/app` y `/admin`. Las pantallas de trading y administración pertenecen a Fases 2 y 3. Contratos TS/Python compartidos se generarán al conectar esas pantallas.
- **Cabecera demo:** se exige en absolutamente todo `/api/*`, incluyendo meta y auth. `/healthz`, `/docs` y `/openapi.json` quedan fuera de ese prefijo. Los clientes Swagger deben proporcionar la cabecera manualmente; el smoke script ya la envía.
- **Red local:** PostgreSQL y Redis sólo están en la red interna de Compose; API y Caddy se publican en loopback. No hay pasarelas, firmas, claves de wallets ni conectores de mercado en Fase 1. Los futuros adaptadores de mercado serán de sólo lectura.

- **Dependencias del frontend:** se mantiene Next.js 14.2.35 según el stack fijo. El registro npm informa vulnerabilidades en esa rama y propone una actualización mayor a Next.js 16.4.6. Se desactiva el optimizador de imágenes y no se utilizan Server Actions, rewrites ni middleware de autorización. Se actualiza PostCSS mediante override a 8.5.33 para resolver sus avisos sin cambiar Next.js. La auditoría residual se detalla en VALIDATION.md; esta fase se ejecuta sólo en loopback y no se publica al VPS.
